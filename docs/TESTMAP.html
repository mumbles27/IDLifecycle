How the stand-ins are kept safe and honest

A fake is only useful if it can't be bypassed and behaves like the real thing. These are the guards and the contract tests behind the dashed wall.

  1. Only the stub module can load

    Every script under test runs in a child pwsh whose PSModulePath holds only StubAD (plus StubEXO for cloud scripts). Before the first test, the runner proves ActiveDirectory resolves to version 99.0.0 in the stub folder, or aborts with SAFETY ABORT.

    Run-Tests.ps1 · TestHelpers.ps1 Assert-StubOnlyEnvironment

  2. Stubs refuse to run without a test state file

    The fake AD and Exchange Online modules throw on import unless IDL_STUB_AD_STATE / IDL_STUB_EXO_STATE point at a JSON file, so they can never quietly stand in for real ones.

    StubAD\ActiveDirectory · StubEXO\ExchangeOnlineManagement

  3. Graph is redirected only to loopback

    The cloud module accepts a different login and Graph URL only with IDL_CLOUD_TEST=1 and only to 127.0.0.1, where FakeGraph.ps1 listens. It verifies the certificate-signed client assertion like Entra ID does.

    IDLifecycle.Cloud.psm1 · FakeGraph.ps1

  4. Setup fakes need a test switch

    The install, uninstall and tray scripts load SetupFakes.ps1 only with IDL_SETUP_TEST=1 and only from the tests folder. Services, ACLs, Program Files and machine variables are simulated in a JSON file.

    SetupFakes.ps1 · FakeDaemon.ps1

  5. Fakes copy the real rules

    Stubs throw where the real cmdlets throw (already a member, not found, unique names, non-leaf deletes). FakeGraph returns the real error codes for mail-enabled, dynamic, synced and role-assignable groups.

    tests/powershell/README.md lists each copied behaviour

  6. Go fakes are held to the script contract

    TestFakeContract and TestFakeRefusesWhatTheScriptsRefuse check that the in-memory ad.FakeClient and cloud.Fake answer like the scripts do, and the PowerShell bridge test runs the real scripts through the real Go client.

    ad/powershell_test.go · cloud/cloud_test.go · engine/pwsh_integration_test.go

  7. Every write is recorded

    Each mutating stub cmdlet and every Graph call is logged in the state file (secrets as ***), which is how the tests prove a dry run made zero changes and a secret never reached a log.

    state.calls · Get-StubCalls · Get-FakeGraphCalls · Get-ExoCalls

From a checkout to a live run

The order to build confidence in. The first four steps never touch anything real; from step 5 on you are checking your own environment, still without changing it until the last step.

  1. Go tests

    Engine, API, store, sources, mail, CLI and the browser end-to-end test, against fakes and a temporary SQLite database.

    go test ./... -count=1

  2. PowerShell tests

    Every script against the stubs. About 20 minutes. Exit code 0 means all passed.

    pwsh -NoProfile -File tests\powershell\Run-Tests.ps1

  3. Mock console

    Click through the console with sample data and no backend, or run its selftest.

    go run ./cmd/idl-mockui

  4. Installer dry run

    Shows every install step without doing it; the setup window calls this Test run (no changes).

    Install-IDLifecycle.ps1 … -DryRun

  1. Health check

    Config, data folder ACL, database, admin user, PowerShell, scripts and the AD module; -cloud also signs in to Microsoft 365.

    idlifecycled check [-json] [-cloud]

  2. Test buttons

    Sources: Test these settings. Settings: Test connection (Microsoft 365), Send test email, Test sign-in settings. Roles: Test this rule.

    the console

  3. Preview impact

    For a role, mapping or lifecycle-group change: every person it would affect, against a live AD snapshot, before you save.

    Roles · Mappings · Lifecycle groups

  4. Dry-run syncs

    A fresh install starts in dry run: syncs plan every change as simulated and never write. Review them in Approvals and History.

    Settings → Engine → Dry run

  5. A script by hand

    Read-only scripts, or action scripts with -DryRun, against your domain to see exactly what they would do.

    docs/TESTING.md → Run one script by hand

  6. Supervised first live run

    Dry run off, manual approvals, a lab OU and a few people. Approve one change of each type and check the result in AD and Entra ID.

    Approvals · Runs · History
