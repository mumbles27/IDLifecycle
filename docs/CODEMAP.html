One sync run, start to finish

A run starts from the scheduler or from Run now in the GUI. Only one run happens at a time. The steps below are the order in engine.sync and engine.Execute.

  1. Fetch every enabled source

    Each source returns normalized records. A failing or suddenly empty source is skipped, and its people are left alone rather than treated as leavers.

    engine/ingest.go → sources/*

  2. Update identities

    Records are saved as identities, keyed by source and external ID. Terminated status or repeated absence marks someone inactive.

    engine/ingest.go → store/entities.go

  3. Snapshot AD

    The managed accounts, their attributes and group memberships come back as JSON. With matching on, accounts without an ID come back too. An empty snapshot while accounts are linked aborts the run.

    ad/powershell.go → Get-IDLSnapshot.ps1

  4. Match people to existing accounts

    People without an account by ID are compared with existing accounts by the matching rules (names, department). A clear match becomes a link; a partial or several matches wait for a person. Admin accounts are never matched.

    engine/correlate.go · identity_pass.go

  5. Plan the differences

    Mappings and role rules render the desired attributes, groups and OU, then a diff against AD gives link, create, update, disable, enable or delete. New account names are checked in AD (sAMAccountName, UPN, mail, CN); a taken name waits for a person or gets a suffix, depending on the conflict mode.

    engine/plan.go · naming.go · identity_pass.go → Test-IDLNames.ps1

  6. Decide each change's status

    The approval policy per change type, the dry-run switch and the delete limits set it to pending, approved or simulated. Old changes no longer planned are superseded.

    engine/engine.go

  7. Apply approved changes

    Grouped by type in a fixed order (links first), at most 50 per PowerShell call. A link sets the ID attribute, can rename the account, and retires the old record. The rolling 24-hour delete cap defers extra deletes.

    engine/executor.go → Set-IDLLink.ps1, New/Set/Disable/Enable/Remove-IDLUser.ps1

  8. Record and notify

    Every transition writes a hash-chained audit row. Failures, pending approvals, tripped limits and identity issues (usernames to choose, matches to verify, accounts nobody matches) trigger email. The matching report is saved for the Matching page.

    engine/audit.go · engine/notify.go → notify/*

Life of a change

How people sign in

Every page and API call needs a session. A local account signs in with a password at POST /api/auth/login (bcrypt, lockout after 5 failures). Entra ID sign-in is optional and follows the steps below. Either way the result is the same server-side session cookie.

Field mapper

On the Attribute mappings page, admins see a source's fields next to AD's user attributes. POST /api/mapper/sources/{id}/fields fetches the source once and reports each field's fill rate and samples. engine.TemplateFields reads every mapping and role-rule template to show which fields are used, and flags the ones the source no longer sends. GET /api/mapper/ad-attributes runs the read-only Get-IDLSchema.ps1, cached for 30 minutes, and falls back to a built-in list. engine.ClassifyAttribute decides which attributes can be mapped.

Install, upgrade and remove

The PowerShell scripts in scripts\ split into two groups. Six run at the service's request against AD. The rest set the machine up, and they call the exe's own init, lockdown and check commands so the rules live in one place.

  1. Build a release

    Copies the exe, the scripts and the Setup.cmd launcher into a protected folder and writes a SHA-256 manifest of every file.

    New-IDLifecycleRelease.ps1 · Setup.cmd

  2. Open the setup window (optional)

    Double-clicking Setup.cmd opens a WPF wizard. It asks for admin rights, checks each page, and runs the installer or uninstaller in a child pwsh, following its log live. Secrets reach the child only through its environment.

    Start-IDLifecycleSetup.ps1 → Install-/Uninstall-IDLifecycle.ps1

  3. Or get it from GitHub or a zip

    -FromGitHub downloads a branch or tag and builds the exe with Go on the server; a release zip is extracted safely. Either goes into a locked staging folder, then that version's own installer takes over.

    Install-IDLifecycle.ps1 -FromGitHub | -SourceDir x.zip

  4. Run that release's installer

    Checks the folder and every hash (or, with -SkipIntegrityCheck, the least safe testing mode, takes the files as they are and writes their hashes itself), copies to Program Files, writes config, locks down the data folder, optionally restores a backup, and creates the first admin.

    Install-IDLifecycle.ps1 → idlifecycled init · lockdown · user add

  5. Register and verify

    Registers the Windows service under the gMSA, starts it, and runs the readiness checks.

    Install-IDLifecycleService.ps1 · idlifecycled check

  6. Tray icon and shortcuts

    Writes tray.json, creates the protected branding folder, and adds the Setup and Tray shortcuts. The tray runs as the signed-in user; Settings, Restart, Stop and Start go through an elevated helper that re-checks the service and runs idlifecycled config set.

    Start-IDLifecycleTray.ps1 → Invoke-IDLTrayAction.ps1 → idlifecycled config set

  7. Upgrade

    Re-run a newer release's installer. It is idempotent, keeps the data folder and restarts the service.

    Install-IDLifecycle.ps1

  8. Remove

    Deletes the service and the installed files listed in the manifest. The data folder stays unless you ask for it, with a backup.

    Uninstall-IDLifecycle.ps1
